# ImagePilot 收费策略 + 运营数据/反馈渠道

> 决策记录（2026-06-15）。结论：**先免费上架攒用户，后期再升级收费；老用户永久免费**。
> 前期**零技术准备**——靠 Apple 自动记录的首次下载版本即可在将来区分新老用户。

---

## 一、收费策略：免费先行 → 后期收费（老用户豁免）

### 路径选型
采用 **B 方案：免费下载 + 内购墙（Freemium）**，而非「整个 app 转付费下载」。
- 老用户：永久免费（见下「版本分界」机制）✅
- 新用户：免费下载、体验后再付费 → 转化高 ✅
- 全程**无后端**（StoreKit / RevenueCat 纯客户端）✅

三种模式对比：

| | 付费下载(A) | 免费+内购(B) ✅ | 订阅(C) |
|---|---|---|---|
| 代码量 | ≈0（改价格） | 集成 StoreKit/RevenueCat | 同 B |
| 新用户转化 | 低（先付才体验） | 高（先体验再付） | 高 |
| 适合 | 价值一眼明确的小工具 | **本 app（功能丰富工具）** | 持续提供价值（云/更新） |

### 核心机制：版本分界豁免老用户（Grandfathering）
StoreKit 收据里有 **`originalApplicationVersion`**（用户**首次下载** app 时的版本号），由 **Apple 服务器保管，跨重装/换机可靠**。

```
设分界线：决定从 vX.0 起收费
收费版启动时读 originalApplicationVersion：
  首次下载版本 < X.0  → 老用户 → isPremium=true，永久免费、不弹付费墙
  首次下载版本 >= X.0 → 新用户 → 走付费逻辑（试用/配额/付费墙）
```
- 也可用 **`originalPurchaseDate`（首次下载日期）** 做分界，更直观（"某日前下载的永久免费"）。
- **关键**：这是 Apple 自动记录的，**前期免费版无需任何埋点**，将来照样能可靠区分。

### 关键真相（纯本地无账号的固有特性）
- ✅ **「谁付过钱」「谁是老用户」可靠** —— Apple 服务器记录，重装/换机不丢，可「恢复购买」。
- ⚠️ **「免费用了多少」不可靠** —— 使用量计数只能存本地，删 app 重装会清零、可被技术用户绕过。
  普通用户不会绕；要 100% 防需后端记账（暂不做）。
  → 因此付费点优先用**身份分界（老/新、付没付费）**，少依赖**使用量配额**。

### 付费点设计建议（待有数据后定）
- **优先「增量收费」**：新增高级能力收费，老能力保持免费 → 体验好、争议小。
  候选 Pro 功能：AI 高清增强无限用 / 时刻秀去水印导出 / 云端分类 / 批量无上限。
- **慎用「给现有功能加配额」**（如"免费只能处理 N 张"）：把免费的变受限，存量用户易反弹。
  若用配额，额度设得不痛（如每月 N 张而非一次性总额）。

### 技术栈（React Native 0.72）
- `react-native-iap`（一次性买断够用）或 **RevenueCat `react-native-purchases`（推荐，尤其订阅）**。
- RevenueCat 直接暴露 `originalApplicationVersion` / `originalPurchaseDate`，有现成「老用户豁免」模式，**仍免后端**。

### 将来收费时的执行清单（现在都不用碰）
1. 集成 RevenueCat/StoreKit + 付费墙 UI + 老用户豁免逻辑 + 「恢复购买」按钮
2. App Store Connect：签 **Paid Applications Agreement** + 填银行/税务 + 建内购产品
3. 申请 **App Store Small Business Program**（年收入<100万美元 → 抽成 30%→**15%**）
4. 改 App Store 文案（"完全免费/无内购" → 说明内购）+ 更新隐私问卷
5. **Sandbox 沙盒测试**（Apple 测试账号，不花真钱）→ 发收费版
6. 对外明确沟通「**早期用户永久免费**」（口碑正面）

### 现在不要做（YAGNI）
- 不接 StoreKit/RevenueCat、不改文案/隐私标签、不埋使用量计数。维持「免费、无内购」。

## 二、用户量看哪里

### iOS（上架后）—— App Store Connect，全部 Apple 免费聚合、不破坏隐私
> 这些是 **Apple 替你聚合的匿名数据**，**不算"你（开发者）收集用户数据"**，所以与「Data Not Collected」隐私标签**不冲突**。等于免费白送你运营数据。
- **Sales and Trends**：下载量、按国家/地区/设备
- **App Analytics**：展示量、产品页浏览、转化率、**活跃设备数 / 活跃用户 / 留存曲线 / 删除率**
- （部分指标需用户在系统「共享 App 分析」中同意，聚合后呈现）

### 安卓（GitHub Release 侧载分发）—— 指标较弱
- 每个 Release **APK asset 的下载计数**（量化下载次数）
- GitHub repo **Insights → Traffic**（views/clones）、Stars/Watch
- 无 Google Play → 没有 Play Console 的留存/活跃数据

## 三、用户需求 / bug 从哪里收集

### iOS
- **App Store Connect → 评分与评论**：用户主动反馈需求/bug，**可在后台回复**
- **崩溃报告**：App Store Connect → 「App 分析/指标」 或 **Xcode → Organizer → Crashes**，Apple 聚合崩溃**堆栈**（用户开启「共享崩溃数据」后），不破坏隐私

### 通用
- **GitHub Issues**：repo 公开可收（适合技术用户；普通用户不会用）
- **app 内「意见反馈」入口（建议补做）** —— 普通用户的**主反馈途径**：
  点击 → 调起邮件发往反馈邮箱（如 chunguangwee@gmail.com），或填简单表单。
  这是目前最该补的运营基建，成本低、价值高。

### 安卓
- 无 Play Console → 靠 **GitHub Issues + app 内反馈邮箱**

## 四、前期（免费版阶段）该专注的事
1. **攒用户**（免费期下载的人将来都是永久免费的口碑基础，基数越大越好）
2. **看 App Analytics 留存/活跃** + **读评论** → 判断将来收哪个功能的钱
3. **加 app 内反馈入口**（见上，建议尽早做）
4. 隐私策略：前期守「零收集」卖点；等真要精细决策再考虑要不要加极轻量匿名统计（会削弱卖点、需改隐私问卷）
