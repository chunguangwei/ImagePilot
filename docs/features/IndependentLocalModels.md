# 独立本地分类方案

状态：随 1.5.90 发布三个独立方案；iOS build 17 用于真机测试，暂不上 App Store。

## 三个主要入口

| 方案 | 用途 | 输出 |
| --- | --- | --- |
| LFM2.5-VL-450M · 标准方案 | 日常分类，419 MB，一次推理 | 一个有效分类 ID＋主体/场景短描述 |
| EmbeddingGemma 2 · 快速分类 | 388 MB，按类别语义相似度匹配 | 分类，不生成描述 |
| Gemma4 E2B · 本地多模态大模型 | 保留现有引擎，侧重细节与复杂内容，速度最慢 | 分类与描述 |

速度和效果会随设备、照片、分类清单而变化；不能保证 E2B 每张都更准确，也未证明 LFM 比纯 EmbeddingGemma 更快。LFM 是产品中的标准选择，不强制替换已选模型。原有物体/场景/CLIP 模型保留在“其他传统模型”下；无模型用户仍可使用内置基础方案。

## 行为与迁移

- LFM 从所有有效内置及自定义分类读取名称、说明和规则；不把图片 OCR 内容作为核心目标。按“先描述＋后分类”生成受约束的 JSON，类别输出采用自然名称，再严格映射到清单内 ID；短描述限制为中文或英文字符，提示词要求约15字/8–12词，并设置96 token输出上限（不保证精确字数），只概括主体和场景，不保留 OCR 数字或外文型号；同名类别加 ID 消歧，描述跟随系统语言。
- 复用已下载的 LFM 文件及校验、续传逻辑，两个文件齐全且 SHA-256 正确才启用。LFM 不依赖 EmbeddingGemma 下载。
- 移除 EmbeddingGemma 下的描述模型开关。旧 embeddingCaption 设置不再触发联合推理；用户模型选择、文件和已有描述保留。用户主动选择 LFM 后，旧版中断的描述任务也可通过继续处理完成。
- LFM 一次模型调用输出分类和短描述，一次数据库更新保存两者。已有描述不覆盖，生成的辅助描述保留在 LFM 元数据中。
- 整次选图先登记 pending；成功为 complete，失败为 failed；停止后已分类但未完成的图片也可从首页继续处理。NA 图片依旧由普通待分类入口恢复。
- 每次 LFM 批处理只初始化一次，逐图清除循环状态；启动前释放共享 LiteRT 引擎，结束或中断后释放 LFM。
- 成功重新分类清除旧置信度、人工分类标记和检测证据；失败保留原分类和原描述，并记录错误。
- API 外部模型仍是用户主动选择的替代方案，不自动调用。

## 验证

自动测试覆盖独立路由、旧描述开关隔离、有效分类规则、非法输出拒绝、单次上下文、停止续跑、手工描述保留和旧证据清理。开发专用原生测试脚本为 scripts/lfm-standard-smoke.js，不用于正式打包。

### 本轮结果（2026-11-06）

- 17 个测试套件、124 项测试通过；Android/iOS 完整 JS bundle 均成功。没有新增原生依赖。
- 隔离 iOS 模拟器、真实 LFM、真实 SQLite：中文和英文各6张，处理2张后停止，再恢复4张；两轮都成功保存6条分类与描述，没有推理/格式/保存失败。
- 中文样本分类5/6符合预期（奖杯误分文档）；英文4/6符合预期（人像、猫误分）。描述仍存在主体细节幻觉，例如把咖啡描述成奶茶。样本很小，不代表整体准确率，也不证明超过 EmbeddingGemma。
- 两轮完整测试分别约29.1秒、25.4秒，含中断重载、数据库和模型加载；不是安卓真机性能结论，也不能和过去仅描述阶段的耗时直接比较。
- 试验过内部 ID 受约束输出、自由文本两行输出；小模型出现类别偏差或漏分类，最终采用自然类别名称的约束输出并严格校验。语法兼容性通过真实运行验证；错误语言仍会被解析器拒绝。
- 仍需 Android 真机和更多用户照片验证速度、准确率、温升。三档是用途选择，不是可靠的准确率排名；未改变现有已选模型，也没有自动调用其他模型兜底。
