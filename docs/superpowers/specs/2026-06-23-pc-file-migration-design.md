# PC 端分类文件物理迁移 — 设计文档

> 日期：2026-06-23。PC 端功能拉齐的第一个**新增功能**（移动端没有，利用桌面文件系统优势）。

## 目标

PC 端允许用户**一键把已分类的照片，按分类物理迁移到「以分类名命名的目录」**。移动端是逻辑分类（DB 记录，照片不动）；PC 端可做真实文件整理。

## 背景与约束

- 照片在 DB 里有 `uri`（PC 端应为绝对文件路径，**实现第一步先核对确认**）和 `appCategory`（分类 id）。
- 分类 id → 中文名：`ConfigService.getCategoryNameMap()`（内置 + 自定义）。
- PC 文件操作走 `ipcRenderer` → Electron main process（已有 copy/delete IPC，**move/rename 需新增**）。
- **关键约束**：移动/复制文件后**必须同步更新 DB 的 uri 到新路径**，否则 app 找不到照片、缩略图全失效。

## 用户流程

1. **分类页（CategoryScreen.desktop）新增「整理到文件夹」入口** → 打开迁移对话框。
2. 对话框：
   - **选目标根目录**（系统文件夹选择框，如 `D:/整理后照片`）。
   - **勾选要迁移的分类**（列出有照片的分类 + 各自张数，支持全选）。
   - **选「移动」或「复制」**（用户每次选）。移动模式弹**二次确认**（原文件会移走）。
3. 确认 → 执行，带**进度条 + 可取消**。
4. 完成提示：「迁移 N 张到 `<根目录>`，失败 M 张（原因汇总）」。

## 目录结构与命名

- 路径：`<根目录>/<分类名>/<原文件名>`，例 `D:/整理后照片/美食/IMG_001.jpg`。
- **分类名清洗**：替换文件名非法字符 `/ \ : * ? " < > |` 及首尾空格/点为 `_`（自定义分类名可能含非法字符）；空名兜底为分类 id。
- **同名冲突**：自动加序号 `IMG_001(1).jpg`、`IMG_001(2).jpg`…，**绝不覆盖、绝不丢文件**。
- **未分类（NA）跳过**：只迁移已分类照片；NA / 待分类的留在原位不动。

## 技术架构（三块）

### 1. 新增 IPC `migrate-files`（main process）
- 入参：`{ items: [{ id, oldPath, targetDir, mode: 'move'|'copy' }], ... }`（可分批传，避免一次过大）。
- main process 对每项：
  1. `fs.mkdirSync(targetDir, {recursive:true})`（目标分类目录）。
  2. 解决同名冲突：目标已存在 → 文件名加 `(n)` 直到不冲突。
  3. `mode==='move'`：`fs.renameSync`；跨盘抛 `EXDEV` → fallback `fs.copyFileSync` + `fs.unlinkSync`。
  4. `mode==='copy'`：`fs.copyFileSync`。
- 返回：`[{ id, newPath, ok, error? }]`。
- 错误隔离：单项失败（权限/磁盘满/源不存在）记录 `error`，不影响其他项。

### 2. DB 同步
- 每项迁移**成功**后，用 `newPath` 更新该照片 DB 的 `uri`（移动、复制都指向**新位置**——按用户要求）。
- 新增批量方法 `updateImageUris([{ id, uri }])`（UnifiedDataService / ImageStorageService），逐张或批量更新。
- 顺序保证：先文件操作成功，再更新该张 DB → 绝不出现「文件移走但 DB 指旧路径」。

### 3. desktop UI（迁移对话框组件）
- 选目录（IPC 调系统文件夹选择框，若无现成则新增 `pick-directory` IPC）。
- 勾分类列表（来自当前分类数据 + getCategoryNameMap）。
- 移动/复制开关。
- 执行进度（已处理/总数）+ 取消按钮。
- 完成汇总。

## 数据流

```
desktop UI
  → 收集选中分类的照片 [{id, uri(oldPath), appCategory}]
  → 算每张 targetDir = 根目录 / 清洗(分类名)
  → 分批 IPC migrate-files
      → main: 建目录 / 解决同名 / move|copy → 返回 newPath
  → 对成功项 updateImageUris([{id, uri:newPath}])
  → 刷新 GlobalImageCache（uri 变了，缩略图要更新）
  → 汇总「成功 N / 失败 M」
```

## 错误处理

- 单张失败（权限/磁盘满/源文件不存在/目标建目录失败）→ 记录原因、跳过、继续其余；末尾汇总。
- 移动成功但 DB 更新失败（本地 SQLite，极少）→ 该张记入失败汇总（文件已在新位置，可让用户重扫修复）。
- 取消：停止后续，已迁移的**不回滚**（移动模式不可逆，故移动前已二次确认；复制模式本就安全）。

## 一期范围（YAGNI）

- ✅ 做：选分类 + 选根目录 + 移动/复制 + 进度可取消 + DB 同步 + 冲突加序号 + NA 跳过 + 失败汇总 + 缓存刷新。
- ❌ 不做：撤销/回滚（靠「复制模式」当安全网）；增量迁移记忆；自定义命名模板；移动端对应功能（PC 专属）。

## 待核实的技术假设（实现第一步验证）

1. **PC 端 `uri` 是绝对文件路径**（移动 + DB 更新都依赖）。若是 `file://` 前缀，统一剥离/补齐。
2. desktop 是否已有「选系统文件夹」「移动文件」的 IPC（已确认有 copy/delete，move/pick-directory 需新增）。
3. `GlobalImageCache` 刷新接口（uri 变更后缩略图更新）。

## 验证方式

- 小批量：选 1 个分类、复制模式 → 文件出现在 `<根>/<分类名>/`，DB uri 更新、缩略图正常。
- 移动模式：原文件消失、新位置存在、DB 指新位置、二次确认弹出。
- 边界：分类名含非法字符（自定义）→ 目录名清洗正确；同名文件 → 加序号；跨盘移动 → fallback copy+unlink 成功；NA 照片不动；中途取消 → 已迁不回滚、停止后续。
